# 剧本：DSH 插件开发

> **方法层**。有人要写一个 `dsh-plugin` 时的标准路径。
>
> 事实细节在 `wiki/topics/plugin-development.md` 与 `wiki/topics/cordis-primer.md`，本页只写"怎么想、怎么查"。

## 第 0 步：先确定要写的是哪一种插件

DSH 的"一切皆插件"意味着插件形态差异很大，**四种形态的骨架完全不同**：

| 形态 | 你在扩展什么 | 先读哪 |
| --- | --- | --- |
| **新工具**（model-facing tool） | 让模型多一种能做的事 | `docs/cookbook/adding-a-tool.md` |
| **新 Provider** | 替换某个能力的具体实现（如换沙箱后端、换存储） | 对应 `packages/<group>/README.md` 的 Service Definition |
| **新 LLM adapter** | 接入一个新模型供应商 | `docs/cookbook/adding-an-llm-adapter.md`、`docs/user/develop/practice/llm-adapter.md` |
| **UI 扩展** | 改 Web GUI | `packages/client/`、`docs/web-styling.md` |

**问清楚要哪种再动手**。最常见的误判：对方说"我要加个功能"，实际要的是新工具，却被引导去写 Provider。

## 第 1 步：吃透 Cordis，而不是 DSH

插件机制的本体在 Cordis 内核（Context / Service / Plugin / Fiber / Registry / 事件模型），DSH 只是在其上的应用。**不懂 Cordis 就写不对插件。**

路由：`wiki/topics/cordis-primer.md` → `upstream/deepseek-harness/docs/cordis-primer.md` → `docs/cordis-tutorial/`（01→07 是完整的渐进教程，07 讲怎么接进 harness）→ `docs/cordis-api/`。

## 第 2 步：认准 capability family 的三件套

DSH 的能力普遍是三层结构，**搞混这三层是最高频的错误**：

```
Service Definition（seam，抽象契约）
        ↑ 扩展插件应该依赖这一层
Service Provider（具体实现）
Consumer（面向模型的 tool）
```

**依赖纪律（上游明确规定）**：扩展插件应依赖 **Service Definition**，而不是具体 Provider。依赖了具体 Provider，别人换实现时你就炸。

查某个能力的三件套分别是哪个包：`wiki/packages/<group>.md` 的"三件套结构"一节，或直接读 `upstream/deepseek-harness/packages/<group>/README.md`。

## 第 3 步：抄最近的同类插件，而不是从零写

在 `upstream/deepseek-harness/packages/` 里找一个**形态相同、最近被改过**的包作为模板：

```bash
cd /Users/majiajun/workspace/DSH-Expert/upstream/deepseek-harness
# 找最近改动过的同类包（近期改动 = 更贴合当前 API）
git log --oneline -20 -- packages/<相关组>/
```

理由：DSH 是 developer preview，API 在变。**最近被改过的包反映的是当前 API，文档可能还没跟上。**

## 第 4 步：配置与 schema

插件的配置 schema 怎么定义 → `docs/user/develop/basic/config.md`。
配置从哪来、怎么覆盖 → `wiki/topics/config-and-tools.md`。

## 第 5 步：测试

上游有完整的测试设施（unit / e2e / web / snapshot / perf / stress 多套 vitest 配置 + pytest）。
路由：`upstream/deepseek-harness/docs/testing.md`、`packages/test-support/`。

注意 `test-support/` 的稳定性标注是 **Support — 兼容性预期较低**，别把它当稳定 API 依赖。

## 第 6 步：发布

- npm 命名约定：官方包是 `@deepseek-ai/dsh-<pkg>`（**包名里不含组名**）；第三方插件不应占用该 scope
- 加 `dsh-plugin` topic 以便被发现
- 路由：`docs/user/develop/basic/publish.md`

## 回答必须包含的四件事

1. **形态判定**（四选一）+ 理由
2. **该形态的最小骨架**（路由到 cookbook，不抄正文）
3. **依赖纪律提醒**（依赖 Service Definition 而非 Provider）
4. **版本基线声明** + 该组的稳定性标注（Product-stable / POC / Unreleased）

## 失败的方法（别再走一遍）

| 走过的死路 | 为什么错 |
| --- | --- |
| 直接照着 cookbook 逐字抄 | cookbook 可能滞后于源码；要用最近改过的同类包交叉验证 |
| 让插件依赖具体 Provider | 违反上游依赖纪律，实现一换就炸 |
| 在 `experimental/` 或 `e2b/` 里找模板 | 前者标 Unreleased、后者标 POC，都不是稳定参考 |
| 忽略 Known Limitations 章节 | 每个包 README 强制带这一节，坑往往就写在那里 |
