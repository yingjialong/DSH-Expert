# 剧本：DSH 报错诊断

> **方法层**。拿到一段 DSH 报错时的标准定位流程。
>
> 这类问题的特点：**静态读源码常常不够**，需要判断是否触发实测。

## 第 0 步：先确定这是哪一类错

三类错的处理方式完全不同，**误判类型会浪费大量时间**：

| 类型 | 特征 | 处理方向 |
| --- | --- | --- |
| **配置错** | 报错提到配置键、路径、凭据、preset、profile | 查配置来源与覆盖顺序 |
| **版本错** | 报错提到不存在的方法/字段/包，或"以前能跑现在不行" | 查版本基线与 rc 间差异 |
| **上游 bug** | 报错来自 DSH 内部、堆栈全在 `packages/` 里、行为与文档明确不符 | 查 postmortem 与 Issues，可能需要绕过 |

判据：**先看报错文本里有没有出现对方自己的代码路径**。有 → 大概率配置错或用法错；全在 DSH 内部 → 才考虑上游 bug。

## 第 1 步：确认版本基线（不做这步后面全白做）

对方跑的是哪个版本？`npx @deepseek-ai/dsh` 默认拿到的是 npm `latest`，不一定是最新 rc（见 `wiki/errors.md` E003）。

```bash
# 让对方给出（或从粘贴内容里找）
npx @deepseek-ai/dsh --version
pip show deepseek-harness-sdk   # Python 侧
```

**版本对不上时，先对齐版本再诊断**——在错误的版本上定位是纯浪费。

## 第 2 步：在源码里精确匹配报错文本

报错文本是最强的定位线索，**直接 grep 原文**：

```bash
cd /Users/majiajun/workspace/DSH-Expert/upstream/deepseek-harness
rg -n --fixed-strings "<报错原文片段>" packages/ apps/ python/
```

技巧：
- 报错含变量时，取**不含变量的最长连续片段**去匹配
- 匹配不到 → 试着去掉标点、换更短的片段；仍匹配不到 → **该报错可能不来自 DSH**（可能来自 Node、Cordis、依赖库），去 `upstream/cordis` 与 `node_modules` 层面想
- 匹配到多处 → 用堆栈里的文件名收敛

## 第 3 步：按类型走对应路由

### 配置错
1. `wiki/topics/config-and-tools.md` 的"配置从哪来、按什么顺序覆盖"
2. `upstream/deepseek-harness/docs/config-catalog.md`
3. `packages/settings/`、`packages/credentials/`、`packages/preset/`
4. 重点确认：**这个配置键在对方的版本里到底存不存在**（配置键会随版本增删）

### 版本错
1. 直接 diff 两个版本间的相关文件：
   ```bash
   git -C upstream/deepseek-harness diff dsh-v0.1.0-rc.7..HEAD -- <相关路径>
   git -C upstream/deepseek-harness log --oneline dsh-v0.1.0-rc.7..HEAD -- <相关路径>
   ```
2. 查 rename/remove 类提交：`git log --oneline --diff-filter=RD`
3. 结论写清楚：**哪个 commit 改的、改成了什么、对方该怎么改**

### 上游 bug
1. `upstream/deepseek-harness/docs/postmortem/`（真实事故复盘）
2. `docs/defensive-patterns.md`（已知反模式）
3. 对应 `packages/<group>/README.md` 的 `## Known Limitations and Deferred Work`
4. 仍无解 → 上 GitHub Issues/Discussions（T3 信源，需标注）
5. 写入 `wiki/open-questions.md`，标 `retry_on_sync: true`

## 第 4 步：判断是否实测

| 情况 | 动作 |
| --- | --- |
| 报错文本已在源码中精确定位、上下文清楚 | **不测**，直接给结论 |
| 报错取决于运行时状态（加载顺序、默认值是否生效、环境差异） | **测** |
| 需要复现对方的真实报错文本 | **测** |

实测边界见 `CLAUDE.md` 第 11 条。要点：`sandbox/` 内最小复现属预授权，**需要真实模型调用的不属于**（花钱，必须停下说明）。

好消息：**绝大多数诊断类实测不需要模型凭据**——配置解析、插件加载、启动日志、报错文本、单元测试都发生在调模型之前。

## 第 5 步：回答与沉淀

回答必须包含：
1. **这是哪类错**（配置/版本/上游 bug）
2. **根因**，带 `文件:行` 锚点
3. **怎么改**，可执行
4. **版本声明**："基于 rc.7；master 上此处已变为 X"（若有差异）

沉淀：
- 报错文本 → 根因的映射写进 `wiki/` 对应包组页的"陷阱"一节（**这是复用率最高的知识**）
- 若我判错了类型或走了弯路 → 写 `wiki/errors.md`
- 若没查出来 → 写 `wiki/open-questions.md`

## 失败的方法（别再走一遍）

| 走过的死路 | 为什么错 |
| --- | --- |
| 先猜根因再去找证据 | 会 confirmation bias 地只看支持自己猜测的代码 |
| 跳过版本确认直接看 master 源码 | 对方跑的可能是 rc.7，master 的代码根本不是他在跑的 |
| grep 报错时带上变量部分 | 永远匹配不到，然后误以为"这不是 DSH 的报错" |
| 匹配不到就下结论"不是 DSH 的问题" | 先怀疑自己的 grep（见 errors.md E002 附带教训：匹配数为 0 时先怀疑正则） |
