# 剧本：版本升级评估

> **方法层**。有人问"我从 rcX 升到 rcY 会炸什么"时的标准流程。
>
> 这是 DSH 特有的高频问题：官方明确警告 **developer preview 会有破坏性变更**，且 rc.7→rc.8 两天内变了 **1604 个文件 / +54064 / −10533 行**。

## 第 0 步：确定两个端点

```bash
cd /Users/majiajun/workspace/DSH-Expert/upstream/deepseek-harness
git tag                                  # 可用的 tag
git ls-remote --tags origin | tail -10   # 远端是否有本地还没有的 tag
```

端点可以是 tag、也可以是 commit。对方说"我用的是 npx 装的"时，注意 npm `latest` 与 `next` 可能指向不同 rc（见 `wiki/errors.md` E003）。

## 第 1 步：变更规模摸底

```bash
OLD=dsh-v0.1.0-rc.7; NEW=HEAD
git diff --shortstat $OLD..$NEW
git log --oneline $OLD..$NEW | wc -l
```

规模决定回答的粒度：**几十个文件可以逐个看；上千个文件必须按信号筛。**

## 第 2 步：按破坏性信号筛（不要通读 diff）

```bash
# 提交信息里的破坏性信号
git log --oneline $OLD..$NEW | rg -i 'breaking|rename|remove|deprecat|refactor!|BREAKING CHANGE'

# 被重命名或删除的文件（最直接的破坏性证据）
git diff --name-status --diff-filter=RD $OLD..$NEW

# 公开接口层的改动（集成方真正会感知的）
git diff --stat $OLD..$NEW -- packages/sdk/ packages/acp/ packages/api/ packages/host/ python/

# 配置层改动
git diff $OLD..$NEW -- docs/config-catalog.md
```

**优先级**：接口/协议 > 配置键 > 包的增删改名 > 内部实现。集成方感知不到内部实现的变化。

## 第 3 步：按八维坐标评估影响面

不要笼统说"有破坏性变更"，要说**对哪种宿主有影响**：

| 维度 | 检查什么 |
| --- | --- |
| 宿主语言 | 变的是 TS SDK 还是 Python SDK 还是协议本身？协议变 = 所有语言都受影响 |
| 运行形态 | 变的是启动方式还是运行时行为？ |
| 并发与会话隔离 | `packages/session/` 有没有动？会话持久化格式变了吗（涉及数据迁移） |
| 沙箱与文件系统 | `packages/sandbox/`、`packages/fs/` 有没有动 |
| 工具复用 | `tool-catalog` 有没有增删工具、工具签名有没有变 |
| 模型与凭据 | `packages/llm/`、`packages/credentials/` 有没有动 |
| 部署环境 | `package.json` 的 `engines` / `packageManager` 有没有提高要求 |
| 版本基线 | npm dist-tag 与 PyPI 版本当前指向哪 |

引擎与包管理器要求的变化最容易被忽略但最致命：

```bash
git diff $OLD..$NEW -- package.json | rg -A2 'engines|packageManager'
```

## 第 4 步：查官方发布说明（T3）

```bash
git log --oneline $OLD..$NEW --grep='release('
```

以及 GitHub Releases / Discussions。**这是 T3 信源，必须与源码 diff 交叉验证**——发布说明可能不完整。源码 diff 才是终审。

## 第 5 步：给结论

回答必须包含：

1. **升 / 不升的建议 + 一句话理由**
2. **破坏性变更清单**，每条带：改了什么、哪个 commit、对方要怎么改
3. **影响面**（按八维坐标说清"对你这种宿主有没有影响"）
4. **数据迁移风险**（会话持久化格式、存储 schema 有没有变）
5. **不确定的部分明说**，写进 `wiki/open-questions.md`

## 沉淀

跨 rc 的评估结果写进 `wiki/topics/版本变更-rcX-到-rcY.md`，这类页面**不会 stale**（历史差异是固定事实），是知识库里少见的长期资产。

## 失败的方法（别再走一遍）

| 走过的死路 | 为什么错 |
| --- | --- |
| 通读上千文件的 diff | 不可能读完，且 90% 是内部实现，集成方感知不到 |
| 只看 release 提交信息 | 发布说明可能不完整，源码 diff 才是终审 |
| 笼统回答"有破坏性变更，建议谨慎升级" | 等于没回答。必须落到"对你这种宿主，具体哪几处会炸" |
| 忽略 `engines` / `packageManager` 变化 | 环境要求提高会让升级在装依赖阶段就失败 |
