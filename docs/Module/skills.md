外部项目的提问通过两种方式进来：人工复制粘贴，或 Claude Code 的跨 session 通讯。两种情况下我都始终在本项目目录内工作，知识库路径稳定。

## 二、三个 skill

| skill | 触发 | 职责 | 关键约束 |
| --- | --- | --- | --- |
| `dsh` | **自动**（任何 DSH 问题）或 `/dsh` | 问答主入口 | 六步流程不可跳步，尤其不可跳过错误本 |
| `dsh-sync` | `/dsh-sync`，或 `dsh` 自检发现落后时调用 | 同步 + 防腐 | 锚点 diff 是核心，不是简单 `git pull` |
| `dsh-wiki` | `/dsh-wiki`、`/dsh-learn` | 维护 + 主动学习 | 学习只能手动触发 |

## 三、`dsh` 的六步流程

```
1 新鲜度自检   git ls-remote 比对本地 HEAD 与远端（秒级，不可跳过）
2 查库         index.md → errors.md → coverage.md → open-questions.md → 命中页 3-5 篇
3 回源核验     rg upstream/ 源码；T1 与 T2 冲突以 T1 为准
4 实测判断     静态可定 → 不测；取决于运行时 → 测；已有 L3 → 不重复测
5 作答         结论先行 + 四种话区分 + 版本差异 + 固定尾部两行
6 沉淀         去项目化写回 + 更新 index/log + 必要时写 errors/open-questions
```

## 四、`dsh-sync` 的十步流程

记录旧基线 → 拉取 → 变更概览 → **锚点 diff 标 stale** → 补学变更部分 → 抽查历史问答 → 重试悬而未决 → 生成版本变更摘要 → 更新基线与汇报 → git 提交。

第 4 步是本 skill 存在的理由。前三步任何人都会做，第 4 步才是"知识不腐烂"的保障。

## 五、`dsh-wiki` 的双模式

- **维护模式**（`/dsh-wiki`）：lint → 查重合并 → 补交叉链接 → 批量复验 stale → 审计 agent 批次 → 矛盾检测 → 覆盖度报告 → 提交
- **学习模式**（`/dsh-learn <领域>`）：定目标等级 → 按等级定义执行 → 沉淀 → 汇报覆盖度变化

**禁止后台无监督自学**——那是"猜测被写成事实"的温床。主动学习只有两个入口：手动 `/dsh-learn`，以及 `/dsh-sync` 后自动补学**已沉淀且上游已变**的部分（目标明确、成本可控）。

## 六、复验优先级（`dsh-wiki` A4）

1. `asked_by: agent` 的（无人纠错过，风险最高）
2. `status: fact` 的（被信任度最高，错了危害最大）
3. `log.md` 中被引用次数多的（高频知识）
4. 其余
